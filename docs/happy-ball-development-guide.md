# 欢乐球球开发经验与维护规范

本文沉淀欢乐球球从视频分析、玩法实现到真机反馈修正的工程经验，供后续小游戏开发、调参和回归复用。它说明已经作出的决策、实际遇到的问题和应遵守的边界；具体交付结果以[验证记录](verification-happy-ball.md)为准。

完整玩法见[设计规格](superpowers/specs/2026-10-28-happy-ball-design.md)，模块接入见[架构说明](architecture.md#欢乐球球的独立边界)，运行命令见[开发说明](development.md#欢乐球球独立验证)。本文不把设计图、自动测试或一次安装成功视为真人手感验收。

## 1. 先确认行为，再复刻画面

视频分析应拆成触地、上弹、顶点、下降、穿层、蓄力、重击、死亡等连续事件。只截几张静态图，容易漏掉液滴、颜料、重击反弹和盘面脱离的时机。

- 记录视频帧率、帧号和时间；比较同一事件前后的连续帧，区分物理运动、镜头运动与形变。
- 优先测相对量：弹跳周期、上升的球直径数、屏幕可见层数。截图中的像素距离不能直接当作世界坐标。
- 原视频不能确定的规则要明确来源。例如黑色竖板的阻挡方式来自用户补充，具体高度和难度曲线是本项目调校值。
- 视频和带水印截图仅用于观察，不作为可直接打包的贴图、UI 或其他授权素材。塔、盘面、球和反馈由本项目代码生成。
- 原视频中出现广告、复活等入口，不意味着本项目也要实现；范围以用户确认的需求为准。

本项目已经确认的行为不能在优化时被悄悄改写：

| 事项 | 当前约定 |
| --- | --- |
| 横滑 | 按住后持续消费横向位移，松手停止转塔，无旋转惯性 |
| 普通接触 | 黑色安全面反弹，普通状态触红死亡 |
| 重击 | 自然连落三层蓄力；首次向下撞横板可砸红，立即计分并上弹，返回穿过碎层后解除 |
| 黑色竖板 | 侧碰拒绝当前转角，不死亡；整个球越过顶面后才能横穿，顶面安全反弹 |
| 盘面移除 | 普通穿层也向左右分成两大块脱离，重击更强；同层不重复分裂或计分 |
| 页面 | 导航中心仅“欢乐球球”，复用现有图标；本局、最高、暂停一行；底部无常驻说明或占位 |

游戏的稳定标识为 `happy-ball`。大厅显示序号取决于合入目标分支后的实际游戏列表，不能把开发时的卡片序号当作跨分支协议。

## 2. 让每一层只拥有自己的职责

| 模块 | 所有权与约束 |
| --- | --- |
| [Core/HappyBall](../Assets/Scripts/Core/HappyBall/) | 球高、球速、塔角、连续碰撞、层状态、计分、重击、随机生成和快照；不依赖 Unity 对象 |
| [HappyBallDragGesture](../Assets/Scripts/Runtime/HappyBall/HappyBallDragGesture.cs) | 纯输入状态机，按完整一帧触点仲裁、换算横向位移、取消与释放门禁 |
| [HappyBallTouchInput](../Assets/Scripts/Runtime/HappyBall/HappyBallTouchInput.cs) | 采集 Unity 触点、射线归属、鼠标兼容和生命周期通知，不决定碰撞结果 |
| [HappyBallPage](../Assets/Scripts/Runtime/HappyBall/HappyBallPage.cs) | 当前会话、固定步调度、暂停、存盘、结算、宿主导航与公共设置接线 |
| [HappyBallSceneView](../Assets/Scripts/Runtime/HappyBall/HappyBallSceneView.cs) | 从快照和模型事件生成画面，管理镜头、资源和有界特效，不反向修改分数或规则 |
| [SaveCodec / SaveStore](../Assets/Scripts/Runtime/HappyBall/HappyBallSaveCodec.cs) | 严格磁盘协议、版本迁移入口、备份与失败恢复；不得读写其他小游戏存档 |

添加玩法先确定属于模型、输入、页面还是表现。不要把一次碰撞的修复写进通用宿主，再用游戏类型判断限制影响；公共组件只承载真正共用的能力。

模型保存稳定状态；碎片、浮字、液滴、触点和相机平滑量属于临时表现。重建页面时根据快照重建当前画面，不回放已经发生的历史事件。

## 3. 固定步、连续碰撞与事件一致性

[HappyBallGame](../Assets/Scripts/Core/HappyBall/HappyBallGame.cs) 使用 `1/120` 秒固定步。页面先汇总候选转角，再分配给本帧实际运行的固定步，不能用渲染帧率直接决定移动距离。

碰撞必须同时考虑球半径、盘厚、扇区侧边与竖板顶面。仅判断球心是否在缺口内，会允许小球擦过实体；仅检查帧末位置，会漏掉快速下落和大角度转动中的接触。

关键不变量：

1. 黑色侧碰撤回本固定步的转角，并按原角度重新计算竖直运动；不能撤回整次手势，也不能停住重力。
2. 输入基线仍随手指推进，已经拒绝的位移不会积压到下一帧；反向滑动应立即生效。
3. 球顶完全低于盘底才记作完整穿层，避免下一层高竖板提前挡住尚未完成的上层通过。
4. 圆角接触要根据接近运动分量区分向下撞击与横向侧撞。曾出现极小横滑把向下红板重击误判成致死侧碰，修复必须覆盖该边界。
5. 分数用整数并处理上限；不能因为动画重播、读档、原点平移或同帧多事件而重复增长。

重击是三态协议，不是按特效颜色判断“无敌”：

| 状态 | 模型行为 |
| --- | --- |
| `Normal` | 自然穿层累计连落；普通落台清零连落 |
| `Armed` | 首次向下接触横板即砸开、计下一档连落分并反弹；安全墙顶反弹保留蓄力 |
| `Spent` | 砸板权限已消耗，完成上弹和返回；通过本次碎层记零分，再恢复普通判定 |

例如自然连落 `+1、+2、+3` 后，重击接触时立即 `+4`，之后通过已碎层不再次加分。下一完整红板仍可致死，拖尾尚未消失不改变规则。

页面一帧可能包含多个模型事件。接触事件携带球高、塔角和原点层，表现层用事件发生时的姿态放置颜料与碎片，不能全部使用这一帧最后的球位置。原点平移时，事件姿态、镜头、活动特效必须换算到同一个坐标基准。

## 4. 随机关卡要同时解决变化、可读性和入口公平性

首版的“三层相近缺口、周期转折”虽然容易证明路线存在，但连续游玩时模式明显，缺少观察与决策。可达不等于有趣，也不等于随机。

当前 [HappyBallGenerator](../Assets/Scripts/Core/HappyBall/HappyBallGenerator.cs) 使用有界结构化生成：

- 每层生成 1～3 个缺口，位置和宽度均变化，转折方向与连续下落长度不固定。
- 缺口随深度总体收窄，但叠加层间波动；最小角宽 `1.025` 弧度，在球轨道半径 `1.35` 处的弦宽不少于三个球直径。
- 同一盘面支持多段红色和黑色区域，不能只做单一红色扇区加一个缺口。
- 保护前层全部合法缺口对应的入场带，不能只保护缺口中心的一条“标准答案”。
- 黑竖板放在黑色盘面内部，并避让整个入场带和自身半宽；不能为凑数量封死入口。
- 入场保护切割可能把红区削成难辨认的细线。小于 `0.18` 弧度的红段转为安全区域，再合并相邻同色段，不把红色扩回保护带。

运行时生成不执行穷举搜索。离线验证调用真实模型，从多个实际入口、缺口边缘和目标缺口重放，覆盖不同种子、深度、长局和快照恢复。

记录样本规模和失败入口，而不是只写“随机关卡全部可达”。有限样本没有证明所有随机状态，更没有证明人类反应、手指遮挡和难度曲线合适。

## 5. 弹跳、层距、竖板和镜头必须一起调

用户反馈暴露出一个典型问题：只提高球的弹跳，旧层距会显得拥挤，旧竖板又显得过矮。尺寸调校需要同时检查物理净空、投影比例和操作时机。

当前关键值集中在 [HappyBallRules](../Assets/Scripts/Core/HappyBall/HappyBallRules.cs)：

| 参数 | 当前值及意义 |
| --- | --- |
| 球半径 / 轨道半径 | `0.22 / 1.35` |
| 上弹速度 / 重力 | `13.2 / 40`；理论上升 `v²/(2g)=2.178`，同高弹跳周期约 `0.66 s` |
| 终端下落速度 | `24`，保留加速落下而非匀速下移 |
| 层距 / 盘厚 | `2.4 / 0.24` |
| 新生成竖板高度 | 早期 `0.85～1.05`，随深度增至 `1.25～1.50` |
| 相机 | 透视、约 38° 俯视、42° 视场角，距离随视口宽高比调整 |

这些是参考视频后调校的项目参数，不是原版源代码常量。世界上升高度约五个球直径，屏幕投影还受透视和镜头基准影响，需要看连续帧。

最高竖板约束来自整个球的净空：`层距 - 盘厚 - 球直径 - 墙高 = 2.4 - 0.24 - 0.44 - 1.50 = 0.22`。碰撞和网格读取同一个 `wall.Height`；不能只拉高网格后宣称障碍已调整。

构图目标为约 4～5 层。计数应关注可辨认的前半环；深处后沿虽然投影在视口内，可能完全被柱体和前层遮挡，不应据此误判密度。长短屏都要同时看球的上方空间和后续层预览。

镜头通常跟随下落和落点基准，不追逐每一次向上弹跳。高竖板顶面反弹时，仅用真实接触抬高落点基准，再平滑移动相机，避免球顶被裁切。

续局还有额外边界：球从高竖板弹起后把墙旋走，此时仅检查当前角下是否有墙，会丢失原落点高度。[ResetFollowHeight](../Assets/Scripts/Runtime/HappyBall/HappyBallSceneView.cs) 根据当前弹道能量推算起点，并只与当前层真实墙高匹配，限制在合法高度内；该推算只影响恢复构图，不修改物理轨迹。回归必须覆盖“高墙弹起 → 高处越墙 → 保存/重入”。

## 6. 反馈效果需要完整的归属与时间语义

[HappyBallPaint](../Assets/Scripts/Runtime/HappyBall/HappyBallPaint.cs)、[HappyBallEffects](../Assets/Scripts/Runtime/HappyBall/HappyBallEffects.cs) 和场景层共同实现液滴、颜料与两大半环脱离。以下问题都曾在连续渲染检查中暴露：

| 问题 | 原因与后续规范 |
| --- | --- |
| 颜料只剩半边 | 角度跨 `0/2π` 的裁剪范围不连续；应以落点为中心展开角域，再与实际实体扇区相交 |
| 已分裂盘面上的颜料漂浮 | 颜料仍属于完整层；按与盘面相同的分裂平面裁分，并转移到对应碎块 |
| 碎块转动后颜料消失 | 透明渲染顺序覆盖了颜料；颜料队列在碎块后，背面剔除避免从盘底透出 |
| 球离地后仍像薄饼 | 把时间区间当作 `SmoothStep` 的输入域；先 `InverseLerp` 归一化，再平滑到目标值 |
| 刚出生的液滴很淡 | 淡出函数参数含义错误；初始应可读，只在生命周期后段淡出 |
| 快速连落时印记位置错误 | 用帧末快照替代真实接触姿态；必须消费事件携带的位置、角度与原点 |
| 读档重播分裂或浮字 | 去重历史仅在运行时建立；恢复时应将已通过/已碎层标记为已表现 |

颜料只能留在实体盘面或墙顶，不能覆盖缺口。盘面旋转时颜料随所属层旋转；左右脱离后，碎块保持脱离瞬间的转角，后续滑动不再带动它。

普通穿层是两块可辨认的大弧形板，不能退化成整层瞬间消失或一团微粒。重击增加打开速度、翻滚和绿色变化，但不拥有额外碰撞或计分能力。

当前资源有界：8 组 / 16 块碎片、64 个颜料记录、96 个液滴。池复用前清除旧归属，层离开窗口、碎块到期、页面离开和资源销毁时分别清理，不能依赖无限增长的历史列表。

## 7. 柱面球影：把设备证据与推断分开

用户补充的测试录屏显示：塔没有转动，仅球弹跳时，球背后的软影会缺失竖条或三角形区域，随后恢复。这不同于正常柔影的整体明暗变化，应逐帧检查局部边缘和缺失形状。

旧实现为独立透明曲面贴在白柱前。几何检查没有发现网格穿入柱体；Metal 上的“正常深度测试 / 强制通过”对照也没有复现缺影。因此不能把“已证明 Android 某驱动或深度格式有问题”写成结论。

结构修正是 [HappyBallColumn.shader](../Assets/Resources/HappyBall/HappyBallColumn.shader)：在柱体自身不透明 pass 中，用柱体局部坐标绘制软椭圆影，删除独立的透明柱影网格。这样不再依赖两层近贴面的深度竞争、透明排序或逐步试出的偏移值。

维护时注意：

- 球影中心高度应在柱体位移完成后转换到柱体局部坐标，避免世界大坐标相减带来的额外误差。
- 移动端的局部坐标插值和椭圆计算保留完整精度；材质变更仍需实际编译与可见性检查。
- [HappyBallShadowChecks](../Assets/Editor/HappyBallShadowChecks.cs) 隔离柱体，覆盖固定重复、整体微移、远坐标和平移后的高度扫描，并记录实际图形 API 与深度格式。
- 桌面诊断只能证明该桌面路径。当前新版已构建安装，用户要求自行检查真机效果，不能把尚未反馈的结果写为“真机闪动已验收”。

## 8. 输入、生命周期与持久化是一条完整链路

连续横滑不能只处理 `DOWN/UP`：必须保留每次 `MOVE` 和最终 `UP` 的末段位移，并按实际游戏视口宽度归一化，不能直接用整屏宽度代替嵌入场景宽度。

同一帧中的第二指和第一指抬起需要整体仲裁，不能因系统枚举顺序不同产生不同结果。多指、取消、失焦、弹窗和离页后，清掉已排队的转角，等待全部释放再获取新手势；真实触摸期间屏蔽合成鼠标事件。

首个触点必须命中实际游戏 Graphic，不能从 UI 或系统边缘滑入后接管。恢复前台、返回游戏和读档均等待明确继续，不自动恢复旧触点。

死亡反馈也需要分层：模型立刻终局、停止输入并保存结果，场景继续播放约 `0.33 s` 的撞击反馈后显示结算。存盘不能依赖动画结束；后台、离页或重开应结束该视觉等待，不允许旧回调重新打开结算。

磁盘契约由 [HappyBallSaveCodec](../Assets/Scripts/Runtime/HappyBall/HappyBallSaveCodec.cs) 与 [HappyBallSaveStore](../Assets/Scripts/Runtime/HappyBall/HappyBallSaveStore.cs) 负责：

- `happy-ball-v1.json` 及 `.bak/.tmp` 独立保存；当前磁盘 schema 仍为 1，规则版本为 2，两者不能混淆。
- 精确验证字段、JSON token 类型、重复键、null、集合、有限数、几何和状态一致性；不依赖序列化默认值补齐损坏数据。
- 分数存为非负十进制字符串，避免跨格式的整数精度问题；文件限制 256 KiB、深度 12。
- 先编码并验证，再写临时文件、flush 和替换；损坏主档不能反过来覆盖已恢复的有效备份。
- 存储失败要保留最后提交的文件并反馈错误，不能把异常当作“本来没有存档”。

层距调整必须通过版本化迁移，而不是放宽新校验去接收旧数据：

1. v1 先按真实旧契约验证：层距 `1.65`、墙高不超过 `0.5`，先拒绝原始穿透、错误层高或损坏状态。
2. 深拷贝后重算层高，球高平移 `(OriginLayer - PassedLayers) × (2.4 - 1.65)`，保留相对当前层的高度、速度、塔角、随机状态和已有墙形状。
3. 早期 Spent 保存的未入账连击按标记补记一次并清零；已经即时入账的 Spent 不补分，最高分同步取最大值。
4. 改为规则 v2，再按新规则完整校验。模型构造和真实 Decode 共用同一归一化入口，重复读取不能再次位移或加分。

旧局已生成的矮墙有意保留，后续新层才使用新高度。检查新难度需要重开新局，不能看到旧存档里的矮墙就断言网格参数未生效；也不能为演示新高度而直接改写用户当前碰撞几何。

## 9. Unity 资源与验证方式

场景使用独立 layer、Camera 和 RenderTexture，不开启全局 3D 物理来替代核心碰撞。暂停要停模拟和表现计时；隐藏页面时停相机、清理临时效果；销毁时释放自己创建的 Mesh、Material、RenderTexture 和程序音效。

曾在 MonoBehaviour 字段初始化中创建 `MaterialPropertyBlock`，触发 Unity 原生资源初始化限制。类似对象放入明确的初始化生命周期，初始化一次、释放一次；不要因创建成功就假定编辑器重载和页面反复进出也安全。

新增 Assets 文件及目录必须带 `.meta`，检查 GUID 不重复。不要提交 `Library/Temp`、测试 `bin/obj`、APK、真机截图/录屏、日志、签名或本机许可。

按改动责任选择验证，而不是用测试数量替代结论：

| 层次 | 入口 | 能证明什么 |
| --- | --- | --- |
| 模型 | `scripts/test-happy-ball.sh` | 实际生产模型的碰撞、重击、生成、长局、原点平移和恢复一致性 |
| 输入 | `scripts/test-happy-ball-input.sh` | 完整触点帧仲裁、取消、释放门禁和位移消费 |
| 存档 | `scripts/test-happy-ball-persistence.sh` | 真实 Json.NET、严格旧档、迁移幂等、临时目录中的备份和写失败 |
| 图形 / 页面 | `scripts/test-happy-ball-ui.sh` | 真实 UGUI/Camera 渲染、长短屏布局、特效归属、生命周期、高墙与恢复构图 |
| 公共宿主 | `scripts/test-minigame-ui.sh` | 合并后的大厅列表、公共图标及既有页面的相关回归 |
| 构建 | `scripts/build-happy-ball-validation.sh` | 当前源码可生成目标 Android 独立包，不证明手感与设备图形正常 |
| 真机 | 明确设备上的交互和录屏 | 实际触控、图形、性能、音效触感和系统生命周期表现 |

视觉问题既要断言，也要查看输出图。只断言球心在屏幕内会漏掉球顶裁切；只测试初始平板会漏掉最高墙上的反弹；只读一张截图会漏掉逐帧闪影。

修复可复现的问题时，保留“修改前失败、修改后通过”的具体用例。历史通过结果只证明当时源码，合并共享页面或构建逻辑后应运行受影响的检查。性能数字注明测量平台，不把开发机均值当作 Android 帧耗时。

## 10. 多工作树、真机与 master 交付

独立包名 `com.duanyao.xanaduyonder.happyballtest` 与正式应用分离，构建入口临时替换产品名和包名，并在 `finally` 恢复。构建后检查 ProjectSettings 无意外残留，依据实际退出码和非空产物确认成功。

`scripts/happy-ball-unity-environment.sh` 使用本工作树的 `Library/HappyBallGradle` 和临时 ADB 端口，避免 Unity 构建影响其他工作的 Gradle / ADB 会话。同一本工作树的 Unity 图形检查和构建仍必须串行，不能共享其他树的 Library 或 Temp。

独立 ADB server 不等于独占物理手机。开发中曾出现另一测试应用安装页面打断操作，之后用户明确指出另一 AI 抢占了 ADB 安装；设备仍在线也不能证明当前命令正常推进。

- 安装和操作始终明确包名、APK 与设备序列，不自动转向其他模拟器或正式包。
- 开始手机交互前协调设备占用；发现其他应用安装或用户正在操作，停止自动触控。
- 安装长时间无结果先核实设备、命令和页面，不把重新启动全局 ADB 当作默认修复。
- 用户要求重试时重新执行目标包安装，只有看到 `Success` 才报告成功；不把发出命令等同安装完成。
- 用户接管试玩后停止自动输入，保留尚未验收的边界，不用频繁截图与触控打断试玩。

向已有新提交的远端 master 交付时，采用以下顺序：

1. 核实当前 worktree、分支、远端和未提交范围；先形成自己的完整代码与文档提交，不能把其他工作树的内容带入。
2. 拉取真实 `origin/master`，查看新增提交与变化文件；在本功能工作树合并目标分支，保留双方历史，不强制覆盖 master。
3. 冲突逐项按行为解决，重点是大厅游戏列表、序号、页面注册/切换、生命周期、公共保存错误、构建入口、README 和测试预期，不能整文件选“ours/theirs”。
4. 合并后检查新游戏与远端已有游戏都在，入口与稳定 ID 不重复，其他页面的暂停/保存回调没有丢失；若目标分支新增横竖屏切换，沿真实页面的方向请求、异步完成和输入门禁接线，旧方向请求完成时不能重新激活已离开的页面。同步文档和实际测试数量。
5. 运行受影响的模型、存档、输入和共享 UI 检查；记录已完成与未完成的设备验证，不因准备交付而扩大成功声明。
6. 推送前重新确认远端是否前进；若前进则再次合并并验证，不使用 force push。推送后核对远端 master 的实际提交与工作树状态。

代码合入 master 与创建正式版本、打标签、上传 Release 是不同动作。用户只要求代码与文档提交时，不自动发布安装包或更改正式版本号。

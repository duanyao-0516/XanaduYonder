# Dino 白边与碰撞间隙诊断

日期：2026-10-28。检查对象为隔离工作树 `p/duanyao.0516/feature/chrome-dino` 的运行时代码 `bd7acb6`，即当前四倍最高速度版本。本次完成源码、原始像素和纯 C# 模型复现，没有修改游戏参数、渲染或碰撞，也未重新打包、安装 APK。

## 确认的原因

1. **原始图集确有白色描边。** `Assets/Resources/Dino/Sprites.png` 是未改动的 Chromium 2× 图集，深灰实体为 `#535353`，周围有不透明白色像素。上游 `offline.ts:1584` 明确说明恐龙和障碍存在 1 个原图逻辑像素的白边，并在外层碰撞框中内缩。原版随后继续用细分碰撞框判断，并非按完整图片矩形碰撞。
2. **当前黑夜渲染保留了白边。** `DinoTrackView` 通过 RGB 增益把深灰提亮到 `#DADADA`，白色像素仍为白色，所以夜间可出现明显亮边。上游 `neterror.css:347` 使用 `invert(1)`，会把白色描边一起变黑。图集没有多出一张图层，问题在于现有图集像素与材质处理。
3. **当前碰撞框包含部分实体外区域。** `DinoCollision` 的矩形并不等同于深灰身体轮廓；腿、躯干、头部等近似框可覆盖白边和轮廓外空白。两轴判定也把仅接触边缘算作命中。把所有矩形统一缩小 1 像素不能保证解决身体轮廓的近似误差。
4. **高速死亡画面可能已越过首次接触点。** `DinoGame.Step` 对一个子步进行扫掠检测，但命中后仍保留整个子步结束的位置，再设置结束状态。途中相交、终点已分离时，停止画面会显示缝隙。`DinoTrackView` 结束时又切换为站立死亡帧，轮廓与先前奔跑／下蹲帧不同，进一步影响肉眼判断。

官方依据：[碰撞入口](https://chromium.googlesource.com/chromium/src/+/3df8d372a3f9d5c38a89d0bc496cc44c85af1feb/components/neterror/resources/dino_game/offline.ts#1584)、[昼夜 CSS](https://chromium.googlesource.com/chromium/src/+/3df8d372a3f9d5c38a89d0bc496cc44c85af1feb/components/neterror/resources/neterror.css#347)。原始文件也保存在本地[参考目录](chromium-dino-reference/source/)。

## 复现证据

独立探针直接编译当前 `Assets/Scripts/Core/Dino/`，从 PNG 生成两套像素矩形：不透明像素，以及排除白色描边的深灰实体像素。2× 图集每个物理像素对应 `1.35 / 2 = 0.675` 游戏逻辑单位。分别对深灰实体与含描边的不透明像素集合求恐龙到障碍的最短距离；距离以游戏逻辑单位表示，不是手机屏幕像素。

| 竖屏逻辑宽 546.667、seed 17、初始启动跳跃后不再起跳，tick 275 | 碰撞子步首次进入比例约 0.071625；首次接触时奔跑深灰实体仍距仙人掌 1.9092，包含白边的像素已接触。终止位置的死亡帧深灰距离约 0.2267。 | 白边／近似框确实能早于可见深灰身体相交。 |

## 现有测试的缺口

`Tests/Dino/AtlasGeometry.cs` 只检查 Alpha，允许矩形至少 70% 被不透明像素覆盖，而且对动画帧取并集。不透明白边也被计入有效身体，因此该检查通过不等于“碰撞框位于可见深灰轮廓内”。例如一个站立腿部矩形按 Alpha 的覆盖率约 93.3%，按深灰实体只有 50%。

## 后续修复边界

- 渲染：分别映射实体和描边的昼夜颜色，验证黑底、白底及圆角遮罩；保持彩色节日帽独立处理。
- 碰撞：以官方外框和细分框为参考，明确坐标原点、比例、动作帧与接触边界语义；用排除白边的实体像素补充回归，不能仅凭统一内缩宣称精确。
- 停止位置：让扫掠返回最早碰撞比例，遍历所有障碍和矩形取最早接触，然后将恐龙和所有障碍统一停在该时刻。跳跃释放／下坠速度钳位和落地切换须保持现有动作契约。
- 速度：官方参数已另行抓取，见[配置参考](dino-chromium-config.md)。当前高速方案与官方参数使用不同单位；是否整体采用原版速度、跳跃、间距及移动端缩放，需要按同一套单位模型实现，不能直接替换三个数字。

本记录确认的是调查与模型复现结果，不代表上述修复已经完成。

# Zuma接入设计：原版 UI、横屏与独立续局

日期：2026-10-27。状态：**已在隔离工作树实现；实际构建与设备证据见[验证记录](../../verification-zuma.md)**。

## 1. 已确认的方案

Zuma作为 XanaduYonder 的独立小游戏：从竖屏大厅进入后，选图、游戏、暂停、结算全部横屏；退出Zuma后恢复竖屏大厅。沿用 Zuma-Deluxe-HD 的背景、青蛙、球、图集、字体、石框、按钮和菜单布局，移植已实现的规则，不重新设计一套现代卡片式游戏 UI。

“原版 UI”在本文中指 **GalaxyShad/Zuma-Deluxe-HD 当前核查提交的高清、16:9 界面**，并非宣称与 2003 年商业版逐像素一致。之前生成的五张效果图是讨论用概念图；实现以源素材、切片坐标和源码布局为准。

移动端采用“按下即瞄准 → 拖动调整 → 正常松手单发”，不需要等待长按阈值；提供独立换球按钮。存档、声音、触感、后台恢复和 Android 返回键服从 Xanadu 的宿主约定。保留原界面皮肤，必要的交互和系统选项做移动端适配。

| 决策 | 本次范围 |
| --- | --- |
| 玩法 | 18 张单链地图 × 4 档难度，共 72 种地图/难度组合 |
| 入口 | 大厅Zuma卡片 → 横屏原风格选图页；有未结束对局时先提供继续/新开选择 |
| 呈现 | 1280×720 参考画布，保持比例，原素材和原布局 |
| 技术 | 纯 C# 规则 + Unity 呈现、输入和音频，共用现有运行时 |
| 存储 | 新增独立 `zuma-v1.json`，保存成绩和完整局内状态 |
| 系统 | 共用 APP 声音/触感开关；离开或后台冻结；回前台由用户继续 |
| 不扩展 | 商业版完整冒险、双链地图、太空关、特殊道具、额外生命、联网与云存档 |

## 2. 核查基线与上游能力

上游固定为 [Zuma-Deluxe-HD @ 28001e0](https://github.com/GalaxyShad/Zuma-Deluxe-HD/tree/28001e0e5061341d502116586626150027242cce)。2021 年 Windows 发布包与这个提交不同，不混用其行为作为当前源码的证明。

Xanadu 核查基线为提交 `42896603043a2a4b8dc4d8c3490f2399880adc5f`，实现分支为 `p/duanyao.0516/feature/zuma-original-ui`，工作树为 `zuma-original-ui/XanaduYonder`。工程为 Unity `6000.3.27f1`、C#、Android ARM64/IL2CPP、OpenGLES3，最低 Android 8.0。保留基线的 2048、跳一跳、旸了个旸及各自存档；不覆盖原工作区中的数独工作。

### 2.1 真实的模式与地图

上游目前只有一套可进入的“选图 + 难度 + 单局 + 结算”流程，内部菜单名为 `MR_GAUNTLET`。主菜单 Adventure 实际进入这套流程，Gauntlet/More Games 按钮没有完整行为。不能按这些按钮数量认定有多种已实现玩法。

18 个稳定地图 ID 按当前顺序为：

```text
spiral, claw, riverbed, targetglyph, turnaround, longrange,
tiltspiral, underover, warshak, loopy, groovefest, spaceinvaders,
triangle, coaster, squaresville, tunnellevel, overunder, inversespiral
```

保存和资源引用使用这些字符串 ID，不使用选择列表下标。所有 18 图和 4 档难度直接可选，不新增解锁系统。XML 中其他 stage/progression 配置、双轨 `blackswirley/snakepit/serpents`、`space` 不进入首期 manifest。`LevelProgression/Level` 的解析和第二轨加载未完成，不能据 XML 条目宣称完整冒险关卡已经可用。

四档参数由 XML 设置索引 `4/8/13/24` 加 `Game_Init` 覆盖组成；每次开局复制为独立配置，避免沿用 C 全局配置被运行时改写的问题。

| 难度 ID / 显示名 | 颜色数 | 初始球数 | 速度/原更新步 | 停止生成的分数阈值 | repeatChance | slowFactor | 默认 ACE TIME |
| --- | ---: | ---: | ---: | ---: | ---: | ---: | ---: |
| `rabbit` / Rabbit | 4 | 40 | 0.80 | 3000 | 40 | 4 | 70 秒 |
| `eagle` / Eagle | 5 | 50 | 0.95 | 5000 | 40 | 3.5 | 100 秒 |
| `jaguar` / Jaguar | 6 | 60 | 0.75 | 5000 | 25 | 1 | 120 秒 |
| `sun_god` / Sun God | 6 | 60 | 1.25 | 5000 | 40 | 1 | 150 秒 |

`singleChance` 均为 6；存在该图、该难度的最佳时间时，作为下一局 ACE 基准。ACE TIME 是成绩比较基准，不是超时失败倒计时。72 是组合数，不是 72 张独立地图。

### 2.2 要保留的规则

| 规则 | 移植约束 |
| --- | --- |
| 球链与插入 | 沿原轨道推进，命中后判定前后插入侧；插入推进完成后，连续 ≥3 个同色球消除 |
| 基础得分 | 插入消除为球数 ×10；第 5 次连续有效消除起，增加 `100+(chainBonus−5)×10`；未消除插入或弹丸射空飞出场地都会打断该连续奖励 |
| 回退连锁 | 断链两端同色时减速回退并在重新接触后检测消除，奖励沿用 `球数×10+combo×100`；这是同色回退规则，不是倒退道具 |
| 终点附近速度 | `BallChain_GetLastMovingBall` 对应球的位置超过轨道样本长度的 80% 时，正常推进速度变为 `ballSpd/slowFactor`；已入洞时按原速度 32 推进 |
| 发射 | 保留后坐力造成的射击间隔、当前/下一球与换球；弹丸原步长 15 参考像素，命中距离平方 `<2300` |
| 金币 | 闲置超过 10 秒出现；出现超过 10 秒闪烁，再超过 3 秒消失；命中消耗弹丸、加 500 分、金币数 +1，并清除 chainBonus |
| 胜负 | 分数严格 `>gaugeScore` 才停止生成；随后清空球链且未入洞获胜。越过终点进入入洞败局，不能改成达到分数立即获胜 |
| 隧道与遮挡 | 按原路径标记和 overlay 呈现、判定；不能射中处于隧道内或爆炸中的球 |
| 时间与结算 | intro 完成后开始有效计时，胜负确定时冻结成绩时间；胜利 Outro 仍会追加分数，最终成绩在 Outro 完成后确定 |

炸弹、减速/倒退/精准瞄准道具、穿隙奖励、额外生命在该提交中没有完整规则链；不能因为图集中有图标或源码中有枚举，就作为“直接移植”的能力。也不新增星级评价、道具商店或闯关解锁。

## 3. 页面与导航

| 场景 | 原版风格与必要适配 |
| --- | --- |
| 选图 | 保留金色神庙、四档难度、关卡缩略图、最佳分数/时间、BACK/PLAY/NEXT；MAIN MENU 返回 Xanadu 竖屏大厅 |
| 游戏待发射 | 保留地图、球链、青蛙、骨石边框、分数/进度条、右上 MENU；增设同风格换球热区及首次触摸提示 |
| 拖动瞄准 | 青蛙朝手指方向旋转，显示克制的方向提示；辅助线只是移动端输入反馈，不新增“精准瞄准道具”或穿透碰撞预测 |
| 暂停 | 原绿底石框 MENU；保留返回游戏/返回选图，增加共用声音和触感开关；移除桌面全屏选项和独立音量滑杆 |
| 结算 | 原绿底石框 STATS、POINTS/COMBOS/COINS/MAX CHAIN/MAX COMBO/YOUR TIME/ACE TIME 和 OK；失败使用原风格 GAME OVER |

从大厅直接进入有效的选图流程，不展示上游无效或错接的 PC 主菜单按钮。选图 BACK/NEXT 只切换地图；暂停中的 RETURN TO LEVEL SELECT 明确返回 Zuma 选图；选图 MAIN MENU 才退出 Zuma。

原菜单保留英文标签与原位图字形；新增继续、错误、重置确认等中文提示复用 APP 已打包的 `Fonts/NotoSansCJKsc-Regular`，在原石框内排版，不把中文字映射到不含中文的原位图字库，也不重复打包另一套中文字体。

未结束对局只有一份。返回选图或大厅会暂停并保留它；再次进入可继续。点击 PLAY 新开局时，如果存在未结束对局，先用原风格弹窗明确“开始新游戏将替换当前进度”，确认后才创建新 session。取消保持原对局。未确认的胜利/失败结果先恢复结果页，OK 后再进入选图。

Android 返回键优先路由给Zuma：活动对局打开暂停；暂停页返回游戏；确认弹窗取消；结果页等同 OK；选图退出到大厅；旋转/加载期间忽略重复返回，交由当前导航操作完成或取消。不能继续走现有 `Update` 中“非大厅一律 ShowLobby”的通用分支。

## 4. 宿主接入与横屏

### 4.1 职责边界

下表对应已经新增的模块。遵循当前 Core 不引用 Unity 的程序集边界，不为 Zuma 重写其他游戏或建设通用游戏引擎。

| 所属路径 | 职责 |
| --- | --- |
| `Assets/Scripts/Core/Zuma/` | `ZumaGame`、球链/弹丸/路径、难度配置、PRNG、防御复制快照；拥有所有影响规则的状态 |
| `Assets/Scripts/Runtime/Zuma/` | `ZumaPage` 导航与局内状态机、视图/原菜单、触摸、`ZumaViewport`、Unity 音频、存档数据/Codec/Store |
| `Assets/Editor/ZumaAssetImporter.cs` | 离线脚本解析 XML/DAT 和生成 manifest；该 Editor 类配置纹理/音频并校验资源，不把 Expat 或 C 指针结构带入运行时 |
| `Assets/Resources/Zuma/` | 仅发布白名单内图集、字体、18 图背景/遮挡、路径数据和转换后音频 |
| `AppController` | 增加Zuma页面路由、宿主进入/退出、方向切换、前后台分发、全局设置读写回调 |
| `Tests/Zuma*` | 编译实际生产源码的规则、输入、存储测试；渲染与设备验证另行执行 |

`ZumaPage` 对宿主暴露进入、挂起、退出、保存和前后台恢复接口；只通过回调申请返回大厅、读取/修改共用设置和报告错误。规则模型不读文件，不调用 Screen/AudioSource，不持有 GameObject。不在 `LocalSaveStore` 中塞入Zuma状态，也不为减少重复代码调整三个旧存档协议。

### 4.2 独立横屏画布

现有 `AppController.BuildCanvas` 与 `SafeDesignFrame` 按 720×1320 竖屏设计。Zuma新增独立 1280×720 `ZumaCanvas` 和自己的适配层，作为现有画布的兄弟节点；不修改所有游戏共用的竖屏常量。只保留一个 EventSystem 和 AudioListener。隐藏旧画布和禁用其射线，不禁用承载 AppController 生命周期的根对象。

进入流程：

1. 停止原页面输入，保存原游戏，关闭旧弹窗，记住大厅滚动位置；生成导航操作 token，屏蔽点击。
2. 请求 `LandscapeLeft`。首期固定一个横屏方向，不随传感器自动翻转；确认屏幕已经横屏、宽高和有效安全区连续两帧稳定后布局，不能把尚未旋转的稳定竖屏误判为就绪。
3. 加载Zuma共用资源和存档，显示选图/继续提示/未确认结果，再放开输入。旋转稳定等待使用前台真实时间，3 秒超时即恢复竖屏大厅并提示失败。
4. 取消或较新的导航使旧 token 失效；资源异步完成不得重新激活已退出页面。加载失败也走统一清理与方向恢复。

退出流程：取消手势 → 冻结并请求保存 → 停止Zuma音频 → 释放关卡资源 → 隐藏横屏画布 → 恢复 Portrait → 安全区稳定后显示大厅、恢复滚动与射线。异常路径也执行方向恢复；持久化失败在大厅显示未保存提示，并保留内存快照以供本次进程重试，不能假装已经写盘。

退出的方向等待同样限制为 3 秒前台时间。系统拒绝竖屏时，在当前安全区内按原竖屏比例显示可操作的大厅并提示，后续前台回调重试 Portrait；不能无限黑屏或锁住输入。该分支是异常恢复，不算横竖屏设备验收通过。

当前 `ProjectBuild.Prepare` 设置竖屏默认方向且禁止横屏 autorotate。实现时需同时核查运行时方向请求、构建设置及生成的 Android Manifest：保证启动仍竖屏且活动可以切入固定横屏，不把 APP 永久改为横屏或无约束自动旋转。最终以实际 APK 为准。

### 4.3 画面与输入使用同一个变换

在 `Screen.safeArea` 内取能容纳 16:9 的最大矩形，统一比例 `s=min(safeWidth/1280,safeHeight/720)`，剩余区域用深色底填充。地图不拉伸、不裁掉终点或轨道；背景、安全区、UI 热区和指针逆变换使用同一个 viewport。长屏两侧余量和刘海/导航区域不接收游戏射击。

源码按左上原点表达布局；Unity 屏幕输入按左下原点，需要在统一适配层转换。路径坐标不能直接当作 1280×720 坐标：上游以 `scale_x=scale_y=1.5` 绘制，球链/金币/终点使用 `((rawX+104)×1.5, rawY×1.5)`，青蛙使用 `((gx+106)×1.5, gy×1.5)`。保留这 3 个参考像素的差异，或在导入时等价烘焙且仅转换一次。

### 4.4 手势所有权

- 只有从有效游戏区域按下的首个指针拥有本次瞄准；按下立即更新方向，移动只更新方向，正常抬起提交至多一次射击命令。
- MENU、换球、弹窗和所有 UI 热区先消费事件，不穿透到场地；其他手指不改变方向、不触发发射。
- 手指移出有效区域可返回继续瞄准；最终在区域外松手则取消。瞄准点与青蛙中心重合时保留上一个合法方向，未形成合法方向则不发射，避免归一化零向量。
- `TouchPhase.Canceled`、失焦、后台、弹窗、退出、旋转均取消所有权；UGUI 的 pointerUp 还要核对底层取消状态。恢复后的旧 UP 不能发射。
- 换球按钮只交换当前/下一球，不发射；触发换球先取消已有瞄准。射击冷却中显示不可发射状态，松手命令被明确拒绝且不延迟排队，不能在用户松开很久后补发。
- 编辑器用鼠标按住/松手验证同一套移动端语义；保留右键换球作为调试便利，不增加移动端隐藏手势。

## 5. 规则移植与资源导入

### 5.1 模拟时间与渲染分离

采用 60Hz 固定模拟步；渲染可以插值，不改变命中、生成或计分。上游仅以 `1000/60=16ms` 限帧，部分状态由 Draw/`clock()` 推进，并不是已经完成的严格 60Hz 模型。因此固定步是本次移植工作：用原参数建立基线，按相同输入序列核对轨道速度、后坐力、插入、爆炸和金币节奏，记录时间换算差异后冻结 `rulesVersion`。

`rulesVersion=1` 明确采用命令在 Tick 前应用、60Hz 固定步、当前球链颜色集生成补充球。上游 C 在移动弹丸后处理发射，使用生成前缓存的颜色集；这些顺序与计时差异属于本次固定步约定。现有测试是源规则断言与 C# 中断重放，不是 C 可执行程序逐帧对照，不能据此宣称逐帧完全一致。

所有影响因果的动画进度进入 Core，包括球爆炸后何时删除、插入何时完成、recoil 何时允许射击、Outro 何时追加和结束。仅装饰性粒子、浮字可以不存储；若某个粒子寿命原本控制 Outro 结束，必须提取为模型计时器，不能直接丢弃。

每步按固定顺序消费输入、推进原规则阶段及计时、完成胜负转换，再生成防御复制快照和表现事件。禁止使用 Unity Physics2D 替代原轨道插入算法。帧卡顿最多补算 5 步，其余丢弃为暂停的墙钟时间，不跳过规则步骤；有效游戏时间只累积实际模拟步。后台不补算离开时间，不使用全局 `Time.timeScale=0` 冻结其他模块。

玩法使用独立、可序列化的 PRNG（`xorshift32-v1`、非零完整 state）；生成球、下一球、颜色纠正、金币位置按固定顺序消费。装饰随机另用独立流，不能影响球序。固定 seed 只是测试输入，存档必须保存当前 state。重放一致性首先针对相同 rules/content 版本的本移植实现；不承诺跨平台与 C 的 `rand()` 序列天然相同。

### 5.2 XML/DAT 导入

编辑期按 manifest 白名单导入 18 图。DAT 从 `0x10` 读取 count，再定位 `0x14+count×10` 读取点数、float 起点，后续读取 `t1/t2/signed dx/signed dy` 并把位移除以 100。校验长度、点数、有限数值、轨道标记、背景/overlay 引用、文件大小写和资源哈希。

原 `pathPos` 是“轨道样本下标 + 小数”，不是世界距离。保留原采样顺序、隧道信息、插值和碰撞尺度，不重新等距采样成样条。所有派生位置由同一个已验证路径定义重建。manifest 包含稳定 mapId、源提交、文件 SHA-256、切片定义和 `contentVersion`；导入失败阻止构建，不在运行时悄悄换一张地图。

### 5.3 必须纠正的上游缺陷

不逐行继承未定义行为：空球链访问、数组越界追加、未初始化颜色、零向量除法、越过轨道后继续索引、对解析器属性缓冲区做 `strtok` 写入、stage 边界检查及 `[18][4]` 成绩数组的错误初始化循环都要纠正。

`isSingle` 在初始化/复制中丢失会改变生成规则；作为明确的纠正项建立固定种子预期序列并记录规则版本。胜利清空球链前捕获最后清链位置，不能照搬下一帧从 `balls[0]` 残留内存启动 Outro。所有修正均限定于内存安全、可恢复性和已声明规则，不借机添加商业版未完成玩法。

球链容量上限 256、活跃弹丸 32；插入/生成前校验。达到上限时保留合法状态，拒绝本次追加且不消费下一球或随机数，记录诊断；正常关卡达到上限视为验收失败，不能靠静默删球掩盖问题。装饰消息/粒子各最多 256，可以按仅影响视觉的策略复用。

## 6. 独立存档与 APP 兼容

### 6.1 文件和所有权

| 文件 | 所有者与本次约束 |
| --- | --- |
| `xanaduyonder-v1.json`、`.bak/.tmp` | 2048 和共用声音/触感设置；协议不变，由原所有者读写 |
| `jump-v1.json`、`.bak/.tmp` | 跳一跳；协议和数据语义不变 |
| `sheep-v1.json`、`.bak/.tmp` | 旸了个旸；协议和数据语义不变 |
| **`zuma-v1.json`、`.bak/.tmp`** | 新增 `ZumaSaveStore` 独占，位于 `Application.persistentDataPath` |

不读写 PC 的 `progress.bin/settings.txt`，不把 PlayerPrefs 当作第二份Zuma存档，不请求额外存储权限。维持应用 ID `com.duanyao.xanaduyonder` 和现有签名/升级路径，保证原 persistentDataPath 继续可达。

上游只保存各图/难度的最佳分数和时间，**完整局内续玩是本次为兼容合集补齐的能力**。成绩和当前对局放在同一Zuma文件中，避免跨文件提交造成重复计分或结果丢失。

### 6.2 版本化数据契约

使用项目已有 Newtonsoft JSON 包，不新增序列化依赖。显式逐项校验 JSON token，不把缺失、null 或错误类型自动解释为默认值；快照深复制后提交给存储层。

| 区域 | 契约 |
| --- | --- |
| 根 | `schemaVersion=1`、`gameId="zuma"`、`rulesVersion=1`、`contentVersion=1`、`profile`、`session` |
| profile | `lastMapId`、`lastDifficultyId`；按 mapId+difficultyId 唯一标识的 72 项 records：`bestScore` 为非负十进制字符串，`bestTimeSeconds` 为非负 Int32 JSON 整数。未完成分别为 `"0"`/`0`；无额外货币/解锁字段 |
| session | 没有对局时必须显式 `null`；否则保存 sessionId、地图/难度、有效模拟时间、全部因果状态、结果状态 |
| 时间 | 模型中保存整数 tick/剩余 tick；结果显示时间为有效 playTicks/60 向下取整秒，沿用原整数秒记录语义；ACE 基准开局冻结并入快照 |
| 大数 | 分数及可能长期增长的 tick 使用非负十进制字符串，边界为 Int64；有限位置/速度可用 JSON number，不允许 NaN/Infinity |
| 标识 | mapId、difficultyId、phase、PRNG 算法均为已知值；ID 对应当前 manifest，列表位置不能代替 ID |

`schemaVersion` 负责文件结构；`rulesVersion` 负责会影响对局重放的规则；`contentVersion` 负责轨道/配置/切片引用兼容性。首期只接受明确支持的版本。将来更新时必须先定义兼容或迁移规则，不因解析成功就用新轨道恢复旧位置。

完整 session 至少包含以下状态；实现时以“恢复后继续输入能否得到同一结果”为判断标准，不能只保存分数和球颜色。

| 状态组 | 必须持久化或从已存数据无损派生的内容 |
| --- | --- |
| 对局/阶段 | sessionId、mapId、difficultyId、`intro/play/lossDrain/winOutro/won/lost`、totalTicks、playTicks、分数、金币总数、ACE 基准、intro/生成/入洞的计数与剩余时间 |
| 球链 | 有序球列表、每球颜色/pathPos/速度/`isSingle`/回退/插入/爆炸/连锁状态、插入和爆炸剩余步；链速度、生成计数、终点标记、chainBonus/maxChainBonus/maxCombo/totalCombos。`isSingle` 影响未来生成，不能仅从颜色推导 |
| 青蛙 | 当前球/下一球颜色、合法瞄准方向、recoil 剩余步；不保存触摸指针或“正按住”状态 |
| 弹丸 | 活跃弹丸的稳定 slot、顺序、位置、方向、颜色；不能恢复时直接清空 |
| 金币 | 位置索引、idle/active/blink/fade 阶段、各阶段剩余时间；所有影响判定的计时 |
| 胜利 Outro | 最后清链位置、是否已初始化奖励、奖励路径 pos/prevPos、已奖励游标、结束等待计时；初始 +100 和后续奖励均不能重复 |
| 随机 | PRNG 算法版本和完整非零 state |
| 结果 | `resultCommitted` 与 `resultAcknowledged` 分开；已确定的最终统计，与本 session 的提交状态一致 |

暂停是运行调度状态，不用一个 `paused` 阶段覆盖底层 play/winOutro 状态。磁盘恢复的未结束对局统一停在暂停提示，明确继续后才推进。胜负已结束且结果未确认时直接显示结果，不重新结算。

初始限制：UTF-8 严格解码，文件最多 256 KiB，读取上限多探测 1 字节；最大深度 12；拒绝重复键、尾随 JSON、未知字段、超容量集合、未知枚举、非法 map/颜色/计数/非有限坐标及跨字段矛盾。先识别根版本，再按版本检查字段，避免把未来版本误判为普通损坏。phase 对应路径合法区间和允许的终点过渡范围必须明确，不能把入洞/Outro 的正常边界状态误拒绝。

超限文件无法在有界读取内可靠判断所有版本字段时返回写保护状态，不回退旧备份、不自动覆盖或重置。根和 session 的版本以任意精度正整数先判断兼容性，再收窄当前版本字段。

256 KiB 上限已用 256 球、32 弹丸、72 项成绩和粒子最大容量夹具验证（76,705 字节），不截断字段或丢弃活跃对象。`PlayTicks` 最大 128,849,018,879，运行到该界饱和，保证整秒成绩可表示为 Int32；`TotalTicks` 保留 Int64 精度。根只允许 `session=null`；其他可空字段必须在协议中逐个声明，不依赖解析器自动填值。

### 6.3 加载结果和写保护

新存储层返回明确的结果状态，而不是统一返回 null。下列保护是Zuma新增设计，不能当作现有三个 Store 已经具备的能力。

| 加载结果 | 行为 |
| --- | --- |
| `Missing` | 主档和备份确实都不存在，创建新 profile；孤立 `.tmp` 不当作已提交存档 |
| `Loaded` | 主档内容和版本合法，加载完整状态 |
| `RecoveredFromBackup` | 主档确定损坏/不存在、备份合法且版本受支持，恢复并提示；修复主档时保护好备份 |
| `Corrupt` | 主档/备份均无法恢复，且不是未知版本或 I/O 错误；禁止自动新建覆盖，原风格提示允许退出，或明确确认重置Zuma数据 |
| `UnsupportedVersion` | 存在需要保护的未来 schema/rules/content 版本，提示需兼容版本打开；不自动降级读旧备份，不自动重置或覆盖 |
| `IoError` | 无法确认内容的权限/读取等错误，提示重试/返回大厅；不当作“无存档”，不自动写新文件 |

有效主档优先，不用较新的备份替代它；但提交前仍需识别待覆盖备份的版本，不能在更新备份时破坏未来版本数据。主档未来版本时立即进入写保护，不回退旧备份；主档损坏而备份未来版本时也写保护。I/O 不可读的文件不能归类为普通损坏。Store 自身强制写保护，不能只靠页面不调用 Save。

确认重置仅用于 `Corrupt`：先把现存主档/备份保留为带时间标识的恢复副本；保留失败则不重置，保留成功才创建新的Zuma文件，不触及其他游戏。未知版本不提供本流程的重置捷径。

### 6.4 提交与失败处理

同一时刻只有一个Zuma写入者，首期在主线程提交最近完整规则步的快照。顺序为：编码并校验完整快照 → 同目录写 `.tmp`、无 BOM UTF-8、独占文件流 → `Flush(true)` → 主档存在时原子替换，不存在时 Move。只有旧主档合法、可写版本时才轮换为 `.bak`；坏主档不能覆盖好备份。启动不提交遗留 `.tmp`。

沿用现有 Store 的原子替换/备份策略，但新增上述版本保护和错误分类。不能仅凭 .NET 临时目录测试宣称 Android 掉电绝对安全；IL2CPP、实际文件系统、后台强杀和替换失败需要设备验证。

保存时机：开局、换球、成功发射、暂停、返回选图/大厅、应用失焦/后台/退出、难度/地图选择变更、终局提交和结果确认；连续运行至少每 2 秒保存一次完整状态。普通同帧请求在当前步末合并一次，不每渲染帧写盘；暂停、离开、失焦、后台和退出回调取消输入并冻结后，必须立即同步提交最近完整快照，不等待下一帧、下一 tick 或重试定时器。focus/pause 双回调按快照修订号去重；上次提交失败则仍允许重试。

突然强杀可能回退到最后成功提交点，周期策略在写盘正常时的目标为最多约 2 秒活动状态；暂停保存成功时恢复到暂停快照。持续写盘失败不具备这个回退上限，必须保持未保存提示。

胜利最终结算必须等 Outro 完成：在一份快照里更新该图/难度成绩、最终统计和 `resultCommitted=true`，先请求持久化再显示稳定结果。失败不更新最佳记录，但同样保存终局。OK 只确认结果并回选图，不能再次加分；`resultAcknowledged` 单独保存。相同 session 的保存重试提交同一逻辑结果，不重复应用奖励。

写盘失败保留内存快照与 dirty 标记，Zuma横屏内显示“进度未保存”，不能只写到被隐藏的竖屏状态栏。活动期间最多每 2 秒自动重试一次，下一次生命周期保存可立即重试；成功才清除提示。结果页可以查看内存中的结果，但不能显示“已保存”或丢弃待写状态。退出后仍持有 dirty 快照，重新进入优先使用它，不以磁盘旧状态覆盖本次进程的新状态。

隔离验收要区分两层：直接调用 `ZumaSaveStore` 时，其他 9 个旧存档文件以及 PC 文件哈希必须不变；完整 APP 的现有 `AppController.Save` 会重写旧游戏和轮换其备份，因此集成验收比较旧协议与有效游戏状态，不承诺所有旧备份字节永远不变。本任务不顺带重构全 APP 的 dirty-save 机制。

## 7. 生命周期、设置与音频

| 事件 | 必须执行的动作 |
| --- | --- |
| 按 MENU/打开弹窗 | 取消指针、停止模拟、保存；关闭后按明确的“继续”操作恢复 |
| Android 失焦/后台 | 先停输入和模拟，再于最近完整步保存；停止音频，幂等处理 focus/pause 双回调 |
| 回前台 | 重算方向和安全区；重建所需视图，停在暂停提示，不自动发射、不补算后台时间 |
| 旋转期间后台 | 使输入保持禁用，前台后继续校验导航 token/安全区；不能用后台的旧宽高宣布布局就绪 |
| 退出Zuma | 保存并释放地图、overlay、粒子、音频和输入订阅；资源引用成对释放，dirty 数据由轻量状态保留 |
| 返回其他游戏 | 方向、画布、相机、EventSystem、声音/触感和游戏续局均正常；不残留Zuma弹窗和热区 |

`OnApplicationQuit` 只是补充，不作为移动端唯一保存入口。保持宿主页面切换的互斥关系；不让隐藏的Zuma继续更新，也不在进入Zuma后继续驱动原游戏。

共用设置仍只有 `SoundEnabled/HapticsEnabled` 两个布尔值。Zuma动态读取宿主当前值，设置修改通过宿主回调持久化到原公共文件，不在 zuma 文件复制一份。原 MUSIC/SOUNDS 两个独立连续音量滑杆替换为 SOUND/HAPTICS 开关，使用原石框/字形/勾选素材，移除桌面 Fullscreen。不能把两个看似独立的滑杆都偷偷映射到同一个布尔值。

宿主 `Save()` 保留原返回类型；设置回调与 `CommonSettingsSaved` 发布公共文件保存结果，Zuma 菜单单独显示“设置未保存”；仍由公共存储所有者重试。Zuma 对局保存成功不能清除公共设置错误，只有公共文件实际保存成功才清除。开关在内存中立即生效，但不能把立即生效等同于已经持久化。

声音关闭同时停止当前音乐和所有Zuma音效，开启后只恢复当前阶段合适的音乐，不重播过期事件；触感只在有效发射/消除等明确事件触发并受公共开关控制。原 `OpenSettings/CreateModal` 的竖屏弹窗不能原样覆盖横屏页，Zuma自己的菜单提供相同设置语义。

上游当前 `bass.h` 是宏 stub，README 也声明声音尚未实现。本次导入 38 个原音效；其中 11 个 Vorbis 1.0 RC1 文件需离线解码 PCM 后由 Unity 重新压缩，其余保持源 OGG。`zuma.mo3` 的 `0/24/28/32/34/36/38/39` 是播放 order。离线通过 libopenmpt 解码为 8 个 subsong，load/main 各含 intro+loop，合计 10 个音乐文件；不把 BASS、SDL 或 MO3 播放运行时塞入 APK。音乐、事件音效、变调、全局静音由 `ZumaAudio` 实现；构建检查全部 AudioClip 可加载及采样信息。听感、长时循环与设备覆盖见验证记录，源码接通不代替实测。

## 8. 素材、包体与发布约束

按场景加载：Zuma公共图集/字体/菜单进入时加载；单图背景、overlay 和路径开局加载；切图和退出释放引用，不同时常驻 18 张地图。不复制渲染纹理，不保留发布包中无用的源图、概念图、参考截图和未接入关卡。禁用不需要的 mipmap、Read/Write，透明边缘和图集采样留足边距。

| 已核查数据 / 估算 | 用途与限制 |
| --- | --- |
| 上游 content 138 文件，35,725,451 字节（35.7 MB / 34.1 MiB） | 原文件体积，不等于 Unity 增量 |
| 全部 64 张图片约 4231 万像素 | 理论无 mip：ASTC 6×6 约 18.88 MB、8×8 约 10.62 MB；ETC2 按 JPG RGB/PNG RGBA 约 31.27 MB |

当前 Android 8/ARM64/GLES3 基线不保证所有设备支持 ASTC。首个保持原兼容范围的单 APK 使用 ETC2 兼容配置；ASTC 只作为已确认支持设备的对比方案，不能把不支持设备的运行时解压成本隐藏在预算里。ETC2 版本不承诺仍在 +20～30 MB，需要在同一基线做正式 BuildReport 和 APK 对比。

已有生产 APK 的一次核查样本为 38,079,817 字节（约 38.08 MB）；按上述 ASTC 预算相加约 58～68 MB，仅用于量级判断。最终报告必须使用同一源码基线、签名方式、构建配置测量“未接入/接入”两个包，并分别给出 APK、安装后占用、加载峰值内存、纹理常驻和帧耗时。压缩 PNG/JPEG/WebP 的源文件大小不能替代这些指标。

本轮 ETC2 nondevelopment 调试签名测量包为 56,109,832 字节，相对上述历史样本约 +18.03 MB；未完成同批重建和运行时性能矩阵，因此这是历史样本量级比较。完整构建条件与已完成/未完成验证见[验证记录](../../verification-zuma.md)。

# 成语接龙：玩法、词库与接入方案

日期：2026-10-26。状态：离线词库、规则与界面已实施；当前设备和自动化验收见[验证记录](../../verification-idiom.md)。

玩法与各页面 UI 的简明开发口径见[成语接龙：玩法与页面说明](../../idiom-game.md)。本文保留详细规则、数据结构和技术接入说明。

已确认需求：独立成语接龙小游戏；APP 在左、玩家在右的对话界面；同字和同音两种模式；左右按钮选择机器开局/人先开始；本局双方不可重复；提示跨局免费无限，但成功展示本局第三次提示即结束并鼓励总结；详情弹窗可加入生词本，游戏页可进入生词本二级页；两套成语数据在本机统一清洗，核心内容为成语、拼音、包含典故的释义。

以下规则细节与实现选择承接已确认需求。初次调研基线为 `4289660`；词库清洗的当前产物和验证结果见[数据说明](../../idiom-data.md)。

## 1. 推荐方向与范围

定位为“离线接龙 + 随手学成语”。APP 根据本地词库接龙，回复和释义可追溯到真实词条，安装完成后的首次使用即可断网游玩。

| 方案 | 优点 | 取舍 |
| --- | --- | --- |
| **采用：两套数据统一清洗、互补核验，本地规则接龙** | 保留双方资料与来源，生成一份统一词库，适合接龙和生词本 | 需要明确字段映射、冲突处理与质量检查，详细资料按需加载 |
| 新华词库单独作为主库 | 数据较小，结构简单 | 四字词较少，故事、用法等信息较少 |
| 在线大模型对话 | 可生成更自由的交流内容 | 增加联网、费用和生成错误问题，不符合本项目首版目标 |

首版包含双模式、开局方选择、完整对局、三次提示后的鼓励小结、详情弹窗、生词本、独立存档、大厅入口和 Android 真机验收。朗读、全局词典搜索、联网排行、真人匹配和多种 AI 难度不纳入首版。

## 2. 玩法与判定

### 2.1 两种模式

首次进入默认“同字接龙”，上方可切换“同音接龙”。两种模式分别保留当前对局和最佳接龙条数；切换模式恢复该模式的对局，不把进行中的链条换一套规则重新解释。

| 项目 | 同字接龙 | 同音接龙 |
| --- | --- | --- |
| 相接条件 | 上条末字与下条首字完全相同 | 上条末音节与下条首音节相同，忽略声调 |
| 示例 | 一心一意 → 意味深长 | 一心一意（yì）→ 一帆风顺（yī） |
| 多音字 | 按字匹配 | 按该条完整成语的语境读音匹配 |
| 当前目标提示 | 请接“意”字开头的成语 | 请接读音“yi”的成语，声调不限 |

同音不合并 `ü/u`、平翘舌、前后鼻音或 `n/l`。例如“长驱直入”的 `cháng` 与“长幼有序”的 `zhǎng` 不相同。拼音原文保留声调用于展示，匹配使用单独生成的规范键。

两种模式使用同一份通过清洗的四字词库。首版接受四个完整汉字的词条；输入仅去除首尾空白，不静默去除内部标点、纠正错字或转换简繁体。词库未收录时显示“本地词库暂未收录”，不武断宣称该词不是成语。

### 2.2 一局的流程

1. 新局先显示并排两按钮：左侧“机器开局”，右侧“人先开始”。这时不产生历史、不随机选词；选择后固定本局开局方，恢复已有对局不再询问。
2. 机器开局：APP 从人工常用开局集合选择一个有后续接法的成语，显示左侧气泡。人先开始：输入区提示“输入一个你想到的四字成语”，首词只校验四字、收录与未用，不要求接字或接音；即使首词让 APP 无词可接，也按真实规则接受。
3. 玩家点击“发送”。除玩家开局首词外，依次检查完整四字、词库存在、双方本局均未用过、符合当前接字或接音。有效输入显示在右侧，计一个玩家完成的成语，APP 随后回复。
4. 每次提交词条后，先检查是否用尽整个可玩词库；若是则显示“词库挑战完成”。否则，APP 无词可接或玩家无词可接均进入本轮小结，说明“这一轮接到这里”；APP 无词可接时可补充“这个词把我难住了”。不展示“失败/机器获胜”。
5. 成功展示本局第三次提示时立即结束，保存最后一次提示供学习，不再接受发送或生成 APP 回复。主动结束也进入小结；新一局重新选择开局方。
6. 主动结束和有进度时重新开局均要求确认。切换模式、查看生词本和返回大厅自动保存，不结束对局。

**去重是规则层约束**：本局双方接受的全部词条组成一个已用集合，玩家输入、APP 回复和提示候选都查询它。有效提交后才占用词条；仅查看提示、填写草稿、查看释义、加入生词本不占用。恢复时从完整历史重建，跨页面或重启不能绕过。新一局才清空该局集合；两个模式不同对局各自去重。若清洗阶段建立了经审核的别名映射，也按同一规范词条 ID 去重。

没有倒计时、体力或输入错误次数限制。错误输入留在输入框中，就地给出具体原因，不进入历史、不计数、不消耗提示或随机状态。

显示“本轮完成 N 个成语 / 最佳 N 个”，N 只计算玩家有效提交，**包括人先开始时的第一词**。机器开局词和回复、仅展示未发送的提示候选不计数；通过前两次提示提交的合法词同样计数。不设置会让用户感到受罚的提示扣分或失败排行。

### 2.3 免费提示与鼓励小结

- 免费不限次数指没有跨局配额、付费、广告或冷却；每局独立统计 0–3 次，第三次有效提示结束本局，新局归零。
- 一次有效提示是针对当前玩家待提交回合，首次成功生成并展示一组最多 3 个合法候选。候选点击只填入输入框，不自动发送。玩家先开始时可以提示常用开局词，也计一次。
- 同一待提交回合只生成一组提示。收起后再次查看、看候选释义、打开生词本、页面重绘和重启恢复都只是查看已有提示，不重复计次；提交一个有效词进入下个玩家回合后，才可申请下一次新提示。按钮需区分“提示”和“查看提示”，避免用户误以为重复消耗。
- 对应候选、回合编号和提示计数在展示前一次性提交并保存；快速连点按同一请求去重。无合法候选或生成失败不计次。提示不消耗 APP 选词随机状态。
- 第三次提示把 `hintUseCount=3`、候选列表和 `endReason=HintLimitReached` 一起提交。直接展示包含候选词的居中小结弹窗，避免提示刚出现就被另一个弹窗盖住；候选可查看并加入生词本，但不能再发送。
- 小结示例：“这轮你完成了 12 个成语！把新认识的词收进生词本，下次又能多接几个。”仅在确实达到新纪录时展示对应提示。0 个词时改为“这次先认识几个新成语，下轮再试试。”，不虚构进步，不写“失败”。
- 小结提供“再来一局”“生词本”和“回看本轮”；关闭小结后保留终局历史，输入区变为“本轮已完成”，并提供“本轮小结”和“再来一局”按钮。前者可再次查看终局候选，退出恢复后仍可使用，不重新计次或恢复发送。

### 2.4 APP 回复策略

- APP 优先选择人工常用表中的词，并评估它留给玩家的后续选择。存在可继续接龙的候选时，避免主动选择立即堵死玩家的词；有多条选择时优先保留至少 3 条后续接法。
- 常用与可接度相近时使用可复现的随机选择，减少每局同一路线。固定候选排序与对局随机状态，恢复对局不会重新抽回复。
- 数据源没有可靠词频字段。常用表是单独维护和核验的产品数据，首版建议整理 300–500 条；不把估计值标成词频。
- 不承诺永远可接或全局必胜；候选不足时如实进入终局，不放宽规则、不编造词语。

## 3. 页面与操作

沿用现有米白背景与绿色配色，APP 气泡靠左、玩家气泡靠右。气泡以成语大字和较小拼音为主，颜色及左右位置共同区分双方。

```text
┌──────────────────────────────────┐
│ ‹ 大厅   成语接龙  [生词本]  ⋯    │
│       同字接龙  |  同音接龙       │
│ 请接“入”开头       本轮完成 1 个  │
├──────────────────────────────────┤
│ APP                              │
│ ┌ 一心一意 ⓘ ┐                  │
│ └ yī xīn yī yì┘                  │
│                    ┌ 意味深长 ⓘ ┐│
│                    └ yì wèi shēn cháng│
│ ┌ 长驱直入 ⓘ ┐                  │
│ └ cháng qū zhí rù                │
│             对话区域滚动          │
├──────────────────────────────────┤
│ 请接“入”字开头的成语             │
│ [提示0/3] [ 输入成语……   ] [发送]│
└──────────────────────────────────┘
```

顶部与输入区的接龙提示来自同一规则状态。新局未开始时，对话区显示“谁来开个头？”及左右并排的 `[机器开局] [人先开始]`。标题、模式区与底部输入固定，对话区填满剩余空间；不会把整页缩成位于屏幕中部的小区域。玩法说明明确“第 3 次提示后回顾本轮”，不让结算突如其来。

- 中央对话可滚动；接近底部时新消息自动跟随，正在看历史时保留位置并显示“新回复”入口。
- 使用气泡复用或虚拟列表，长局不会为所有历史同时保留 GameObject。按下后发生滚动拖拽，不触发详情点击。
- APP 回复是本地计算。可用约 150–250 ms 的轻量出现动画，但动画不作为规则层的输入锁；后续有效操作可以结束当前表现并基于已提交状态继续。重复点击同一次发送只提交一回合。
- 默认依靠明确的“发送”按钮。输入法的选字、回车、失焦和 `onEndEdit` 均不直接发送；拼音组合尚未提交时提示先确认汉字。
- 不在输入过程中把字符上限设成 4，否则会截断拼音组合。提交时才校验四字；草稿设置合理的独立长度上限，防止超长粘贴。
- 新一局、主动结束和玩法说明放在页面菜单，避免挤占聊天区域。终局保留完整历史和查看释义能力。

### 3.1 释义弹窗

点击双方任意有效成语气泡，复用公共 modal 容器，显示居中对话框。宽度不超过安全区的约 90%，高度不超过约 75%；标题与关闭按钮固定，正文独立滚动。

显示顺序为：成语与拼音 → 释义（含“词义、典故、出处”有内容的小节）→ 可选例句。长典故可展开，缺失时不显示空栏目，也不把出处自动改写成完整故事。近反义词和语法用法不展示。底部主按钮“加入生词本”，加入成功后变为“已加入”；同时提供“复制成语”和关闭入口，并以轻量文字展示资料来源。来自聊天、提示、小结、生词本列表的词条都复用同一详情。

打开详情收起键盘并保留草稿、对话位置；关闭后恢复原位置，不自动弹出键盘。蒙层阻止底层发送与点选。正文按纯文本渲染，关闭 RichText 解析，不把外部数据当作标记或操作指令。

### 3.2 生词本二级页

游戏页右上方提供小尺寸“生词本”按钮，开局前、进行中和结束后都能进入。生词本跨对局、跨模式共用，列表按最近加入排序，每项显示成语、拼音与一行释义摘要。点击条目打开同一详情弹窗；已加入的条目显示“已加入”，另提供明确的“移出生词本”动作，不让重复点击加入按钮意外移除。

同一词条只保存一份；重开不清空生词本。空列表提示“点开成语，加入想记住的词”。首版提供列表查看、详情、加入和移除，不加入背诵计划、熟练度评分或全库搜索。进入只结束视觉动画并保存对局，返回恢复原模式、草稿、聊天位置和终局状态。

### 3.3 Android 中文输入与返回键

现有安全区布局不能代替键盘避让。Unity 6000.3 的 `TouchScreenKeyboard.area` 在 Android 返回零矩形，不能据此估算键盘高度。[Unity 官方说明](https://docs.unity3d.com/6000.3/Documentation/ScriptReference/TouchScreenKeyboard-area.html)

- Android 11+ 使用系统 IME insets；Android 8–10 使用可见窗口区域兼容方案，转换到实际 Canvas 坐标。
- 区分窗口已缩放和键盘覆盖，避免重复上移。输入栏贴在可见键盘上边沿，对话区相应缩短；关闭后恢复安全区布局。
- 浮动键盘可能没有底部 inset，不能以高度为零推断键盘已关闭。
- 区分“输入法抢焦但 APP 仍在前台”和真正进入后台。Android 弹出键盘会触发 Unity 的失焦回调；现有 shell 以 `focused` 阻止输入，不能直接照搬到文字输入页。依据平台前台/暂停状态与 IME 状态处理：输入法抢焦保留编辑和发送能力，真正 Home/暂停仍停止表现并保存，不能仅凭键盘可见就忽略所有失焦。[Unity 生命周期说明](https://docs.unity3d.com/6000.3/Documentation/ScriptReference/MonoBehaviour.OnApplicationFocus.html)
- 返回键顺序：关闭当前弹窗 → 收起输入法 → 生词本返回游戏 → 游戏返回大厅 → 大厅退出确认。若 Android 已消费返回键用于隐藏输入法，不再向下派发一次页面退出；详情从哪里打开，就回到哪里。
- 保留 UGUI 和现有输入系统。新增窄范围 Android 键盘桥接，不迁移整个 APP 的 UI 框架。

需要真实中文输入法验证九宫格/全键盘、候选选字、长拼音、粘贴、回车和快速连续输入；ADB 的文本注入不能替代这部分验收。[Android IME Insets](https://developer.android.com/reference/android/view/WindowInsets.Type)

## 4. 词库调研结论

本次已下载指定版本的原始 JSON 进行统计，结果不是照抄 README。

| 指标 | 京墨独立数据仓 | chinese-xinhua |
| --- | ---: | ---: |
| 实际记录数 / 唯一词条数 | 49,639 | 30,895 |
| 唯一四汉字词条 | 45,776 | 29,502 |
| 四字且释义非空 | 45,772 | 29,502 |
| 上述条目中基础四音节语法通过 | 45,764 | 29,492 |
| 原始文件总大小，十进制 MB | 26.60 | 10.32 |
| 四字且有释义的紧凑 JSON，gzip MB | 7.60 | 3.41 |

语法通过不等于词条或读音已逐条校对。京墨上述候选仍需处理已知错字、拼音异常、字体缺字和人工排除项；45,764 是清洗前的候选规模，不作为最终发布条数承诺。

新华 README 标注 31,648 条，但固定版本 JSON 实测为 30,895。两库共有 30,858 个词条，按同名合并后共 **49,676** 个词条。新华独有的 37 条中没有完整四汉字词条，仍进入本机整理资料库并标记质量问题；统一库导出一个游戏子集，不重复打包两份数据。

两个源的原始字段都保留在开发快照里，但产品只使用本节规定的统一字段。京墨的结构化 `story` 共有 **3,961** 条，是短典故梗概，约覆盖合并资料库的 **7.97%**，并非每个成语都有完整故事；四字条目中有 3,548 条带此字段。不能以出处替代故事，也不自动编故事补齐。

本轮额外核对发现：同名拼音规范化后仍有 **398** 条带调差异，其中四字词有 **353** 条；这些是待核对差异，不表示某一仓库必然错误。释义规范化完全一致的有 17,213 条，诊断时忽略标点后相同的有 28,184 条；其余差异不能简单拼接或凭字符串长度决定。京墨还存在词义/读音错配样本，故不能“整条记录无条件主库优先”。

### 4.2 统一字段规范（建议定稿口径）

对用户仍只有三个核心内容：**成语、拼音、释义**。释义内部允许词义、典故和出处分段，另外保留一个可选的例句区；不要把所有来源字符串直接拼成一个无法纠错的大字段。

| 统一内容 | 必需性 | 源字段与规则 |
| --- | --- | --- |
| `word` 成语正文 | 必需 | 两库 `word`；保留规范正文，以稳定 ID 关联，审核过的错字修正留痕 |
| `senses[].pinyin` 带调拼音 | 游戏词条必需 | 两库 `pinyin`；与该义项绑定，显示用标准带调文本，另存规范音节数组 |
| `senses[].explanation.meaning` 词义 | 游戏词条必需 | 两库 `explanation`；清理格式，修正有证据的问题，不生成新释义 |
| `senses[].explanation.stories[]` 典故 | 可选，纳入释义 | 京墨 `story`；保留段落、绑定正确义项，缺失为 `[]`，不凭出处自动扩写 |
| `senses[].explanation.origins[]` 出处/引用来源 | 可选，纳入释义 | 京墨 `source` 和新华 `derivation`，统一为 `{text, reference}`；无法可靠拆书名时原文放入 text，reference 留空 |
| `senses[].examples[]` 例句 | 建议保留，可选 | 两库 `example` 和京墨 `quote`，统一为 `{text, reference}`，去除本词内重复内容 |
| `id / senseId / gameSenseId` | 内部必需 | 稳定标识、义项标识、该词用于接龙的已审核默认义项；不是给用户展示的字段 |
| `provenance / quality / versions` | 内部必需 | 字段来源、repo/commit/文件/原 ID、质量标记、修订依据、规则与词库版本 |

**近义词、反义词、拼音缩写不进入产品词库。** `usage` 多为“作宾语、定语”等语法标签，首版也不展示或打包；原始材料保留在开发快照中，未来需要时可重新导出。例句有助于理解和复习，保留有内容的记录即可，不要求每个词齐全。

`senses` 用于正确保存多义、多音，不意味着首版增加复杂的选读音交互。普通词只有一个义项。像“一日之长”可能分别指年长（zhǎng）和长处（cháng），拼音、词义、出处、典故必须按义项绑定，不能混成一条。首版游戏每词只采用一个经核验的 `gameSenseId`，两个模式共用；未能确定的词暂不进入游戏子集，不同时把所有读音当合法接音。当前游戏详情默认展示游戏所用义项，生词本记录该义项，便于一致复习。

外部缺失、null、空字符串和明确占位值在导入边界处理：可选数组统一为 `[]`，引用缺失统一为空字符串；必需字段缺失标为待补齐，不能用“暂无释义”冒充释义而放进游戏。新华 `derivation` 有 6,850 条字面“无”，`example` 有 19,208 条“无”，这些必须按缺失处理。占位判断针对资料字段，不对词条正文机械替换。

### 4.3 全量本机清洗与合并规则

整理范围是两个仓库的**全部成语记录**，不扩展到汉字、诗词等其他数据集。产物分三层：固定原始快照 → 一份统一资料库（含不可玩/待审核记录）→ 随包游戏词库。所有输入记录必须能追踪到去重后的词条或隔离清单，禁止静默丢弃。

1. **固定与保留来源**：五个京墨分片和新华完整文件均固定 commit/SHA256；保留原始记录和文件，不原地覆盖，导入脚本完全离线也能从缓存重跑。
2. **结构与格式**：严格校验字段类型、null 和数组元素；UTF-8、正文 NFC、首尾空白及换行统一。拼音单独规范大小写、空白与分隔符，可映射 `ɡ→g`；不删除有语义的汉字、数字或标点，不自动简繁转换，不靠相似字猜修正。
3. **按词归并**：同名词归于同一稳定词条，保留双方来源。同一字段完全相同只留一份；空缺互补。别名、异体、错词只有经审核映射后才合并，不能模糊匹配。非四字资料仍保留在统一库，标记不可参与首版接龙。
4. **文字差异分级**：内容等价、仅格式或标点差异时保留结构更完整的版本，记录另一来源。释义有实质差异时保留待审核版本，不直接拼接、不只取最长。京墨的结构化信息通常更便于使用，但不能整条无条件覆盖新华。
5. **拼音与义项核对**：做带调及无调两组对照。正文、核心释义或拼音存在未解决关键冲突的词进入隔离清单；确认是多义多音时拆分绑定义项，并明确游戏义项。含问号、连写等格式异常也必须有修订依据后才能进入索引；去声调时保留 `ü` 的区别。
6. **典故与例句整理**：`source/derivation` 归出处，`story` 归典故，`quote` 归用例；不把引用文本都标成完整故事。去重仅在同词同义项内做，多个成语共享一个典故正常，不跨词删除。含“～”的例句仅在含义明确时用本成语替换用于展示，保存原文与替换记录；不自动把古文改写成白话。
7. **修订与质量清单**：所有人工修正记录旧值、新值、原因、核验来源；记录缺字段、读音冲突、可能错配、字体缺字和不可玩原因。譬如“击石弹丝”的京墨记录有词义/拼音错配，“屏气凝神”从新华补出的释义仍有疑似错字，不能因“补齐”就视为通过。
8. **导出与验证**：只导出四汉字、字体可显示、有真实释义、四音节可解析且已解决已知关键冲突的词；按稳定排序输出索引、详情和来源清单。两种模式使用同一游戏子集。验证唯一 ID、引用完整、无占位、音节与词义绑定、可重复生成一致摘要；清洗统计逐项列出接收、合并、补齐、修正、隔离和排除数量。

开发侧建议保留 `Data/Idioms/source-manifest.json`、`overrides.json`、`common-idioms.json` 与 `scripts/import-idioms.py`；完整原始/统一中间产物留在忽略目录，报告和必要修订表可进入仓库，最终运行资源正常版本管理。Python 只参与开发数据处理，不进入 APK。

这一阶段先完成规范和完整差异清单，再执行确定性的清洗导出。字段格式通过不等于内容逐条考证正确；发现新问题通过有来源的修订表持续改正，不用模型自由生成来填满字段。

### 4.4 打包与加载

运行资源已由 `scripts/pack-idioms.py` 写入 `Assets/Resources/Idioms/`：一个 gzip 目录索引，详情按最多 256 条分片，按稳定词条标识查找。清洗审计资料保留在 `artifacts/idiom-cleaned/`，不整体打入应用。ID 由规范化词条确定性生成，不使用原始数组下标。

首次进入该模块才加载目录并建立首字、首音节索引，大厅启动不反序列化全部词库。点击成语时只加载相应详情分片，使用按字节上限控制的小型 LRU 缓存；离开时释放详情对象和资源引用。词条索引可以在本次 APP 进程内复用。继续使用现有 Newtonsoft JSON，不引入 SQLite 或新的运行时。

此前完整京墨四字资料压缩约 7.6 MB，是旧字段集合的参考值。此次裁掉近反义词/用法、合并去重并增加义项与来源信息后，需要重新生成再测量，不沿用旧包体估算作为承诺。实现后比较构建前后 APK、安装占用和运行内存；避免把压缩文件大小当作托管对象内存占用。

## 5. 状态、存档与异常

### 5.1 规则层拥有完整回合

`IdiomGame` 是本局状态唯一来源，纯 C# 且不引用 Unity。UI 不能自己追加有效历史或决定胜负。

一次有效提交的流程为：校验玩家输入 → 确定 APP 回复或终局 → 一次性提交完整回合与记录 → 尝试原子写盘 → 展示双方气泡。回复不依赖定时器才进入存档；出现动画只是已提交状态的表现。机器首词由独立的开局动作提交；玩家首词仍沿用提交链路，只免除首尾匹配。提示是独立状态动作，第三次提示只提交小结与候选，不额外产生一条玩家或 APP 消息。

离开页面、切换模式、打开弹窗、暂停或真正的应用失焦时立即结束尚未完成的表现，按模型重绘；仅 IME 抢焦时不清空编辑或锁住发送。恢复时不会重复追加 APP 回复、重抽随机数或重复增加最佳记录。计算、保存、呈现通过回合编号去重，旧页面的详情异步结果通过请求标识失效。

### 5.2 独立持久化

新文件为 `Application.persistentDataPath/idiom-v1.json`，固定 `gameId: idiom`，配套 `.bak/.tmp`。不修改 2048、跳一跳、旸了个旸或并行新增游戏的存档格式。

建议保存字段：schema、gameId、词库版本及摘要、当前模式、两个模式各自的会话 ID/开局方/词条历史/状态/终局原因/随机状态/草稿/提示事件/最佳完成数量。新局未选择时为 `AwaitingStarter`，无历史也无确定开局方；选择后固定 `firstActor`，角色由它与历史序号推导，不能再假定 APP 永远先说。已用集合、当前接字/音、当前数量从校验过的历史重建。

提示事件最多三条，记录所对应的玩家回合编号和候选 ID；事件数派生提示次数，避免两个计数源。当前回合已使用的提示和第三次终局提示均随存档恢复。候选必须按其发生时的历史验证，不能用最终已用集合误判前两次后来已被提交的提示词。`HintLimitReached` 必须对应三个提示事件，并且第三次之后没有新的消息。新局重置该局提示与历史，切换模式或进入生词本不重置。

解码严格验证字段类型、模式与开局方枚举、历史合法性、无重复、相邻匹配、提示事件及终局一致性。历史数不超过该版本的可玩词条数；两个模式总文件设置 4 MiB 上限，正文释义不写入对局存档，不沿用叠牌游戏的 128 KiB 限制。

使用现有存档的临时文件 flush、原子替换、合法备份恢复语义。写入失败保留旧合法存档，允许继续玩并明确显示“当前进度未保存”；后续保存成功清除该提示。草稿变化防抖保存，已提交回合和暂停/离开立即保存；IME 未完成组合不当作已发送成语。

主档损坏时尝试合法备份；均损坏则保留坏档供诊断并提示重新开局。词库版本不兼容时保留原文件，明确提示重新开始，不静默重新判读旧链条；首版不实现旧版本迁移。

加载结果区分“正常 / 已恢复备份 / 无历史存档 / 损坏 / 词库不兼容 / 目录未就绪”。后三种状态关闭自动写入，禁止草稿、失焦、离开等回调用空对局覆盖原档。用户确认重新开始后，先将需保留的原档安全归档为诊断文件，成功后才启用新档写入；归档失败保留原文件并报告。首次无存档时，只有目录加载及新局初始化成功后才能保存。

### 5.3 生词本持久化

独立文件 `idiom-notebook-v1.json` 及其 `.bak/.tmp`，保存规范词条 ID、当前游戏义项 ID、加入时间与数据版本；与对局的已用集合和提示次数完全分离。同一成语只保留一项。加入、移除采用原子写入，成功落盘后才更新“已加入”或移除列表项；失败则保持原状态并提示重试。重复加入幂等，重复操作或跨入口不会产生两份。

每项同时保留加入时的成语、拼音和简短释义快照，供词库版本变化或词条暂不可用时显示；只有保存的词条 ID 与义项 ID 在当前词库中同时存在且兼容，才优先显示当前完整详情。不能因为词条仍在，就静默换成另一读音或新的默认义项。无法解析的旧项显示保存内容和资料暂不可用提示，不随重开、坏档恢复或新词库自动删除。文本快照有明确长度上限，整份文件按最大词条数和序列化后字节限额校验，不能直接复制对局文件大小限制。

生词本独立执行“主档 → 合法备份 → 保留损坏文件并阻止覆盖”的恢复路径。主档与备份均损坏时，不能把它视为空列表再由下一次加入覆盖；用户确认重建且诊断归档成功后才允许新建替代文件，归档失败继续保护原档。生词本异常只影响收词和查看，不阻止正常接龙。

### 5.4 异常界面

- 目录索引缺失或校验失败：显示模块加载失败和重试入口，其他小游戏仍可进入。
- 某条详情分片读取失败：保留已验证的成语与拼音，显示“详情暂不可用”和重试，不破坏对局。
- 错误输入：就地提示“请输入四字成语 / 本地未收录 / 本局已经用过 / 需要接某字或某音”，保留草稿。
- 可选字段缺失：省略对应小节。字体覆盖在导入阶段校验；真机补验罕见字显示。
